# CarZone – Database (MySQL 8 / TiDB Cloud)

> The same scripts run unchanged on a local **MySQL 8** and on **TiDB Cloud Starter**
> (MySQL-compatible, used for the public demo – see `docs/DEPLOYMENT.md`). TiDB notes: TLS is
> required (`DB_SSL=true`, port 4000); tables with AUTO_INCREMENT carry the TiDB-only option
> `/*T![auto_id_cache] AUTO_ID_CACHE=1 */` (MySQL treats it as a comment) so ids keep insertion
> order like MySQL; CHECK constraints are parsed but only enforced by TiDB when
> `tidb_enable_check_constraint` is ON; no triggers, procedures, events, SPATIAL or FULLTEXT
> are used.

* Database: **`carzone_db`**, character set `utf8mb4` / `utf8mb4_unicode_ci`, engine **InnoDB**
  (transactions + foreign keys + row locks).
* Files: `database/schema.sql` (tables), `database/seed.sql` (demo data, generated by
  `npm run db:build-seed`), `database/carzone_db.sql` (both together — run this one in Workbench).
* Driver: `mysql2/promise` with a **connection pool** (`src/db/connection.js`), prepared statements
  (`execute` with `?` placeholders), `dateStrings` and `decimalNumbers` enabled.
* Money columns end in `_paise` and are integers (₹499.50 → `49950`) — no rounding errors.
* Seed dates are relative (`DATE_ADD(CURDATE(), INTERVAL n DAY)`) so the demo always has
  upcoming and past bookings whenever you import it.

## 1. Entity overview

```
users 1─* vehicles, addresses, sessions, password_resets, cart_items, wishlist_items
users 1─* bookings *─1 services        bookings 1─* booking_addons *─1 addons
bookings *─1 time_slots ; slot_inventory (date, slot) counts seats used by bookings + fitments
services 1─* service_prices (per vehicle type) ; services *─* addons (service_addons)
product_categories 1─* products *─* car_models (product_compatibility)
products 1─* stock_movements, order_items, product_reviews, cart_items, wishlist_items
users 1─* orders 1─* order_items ; orders 1─* order_status_history
coupons 1─* coupon_redemptions (→ booking XOR order)
payments (→ booking XOR order) 1─0..1 refunds
```

## 3. Normalisation
* **3NF** for master data: prices live in `service_prices`, compatibility in a junction table,
  no repeating groups (JSON is used only for display-only lists such as product specs).
* **Deliberate snapshots** (denormalisation) in `bookings`, `booking_addons`, `orders` and
  `order_items`: name/price/address are copied at purchase time so later price changes never
  alter old invoices — a standard accounting practice.

## 4. Indexes
Besides primary/unique keys: `bookings(user_id)`, `bookings(booking_date, time_slot_id)`,
`bookings(status)`, `orders(user_id)`, `orders(status)`, `orders(created_at)`,
`orders(fitment_date, fitment_slot_id)`, `products(category_id)`, `products(is_active, is_featured)`,
`product_compatibility(car_model_id)`, `payments(booking_id)`, `payments(order_id)`,
`payments(status)`, `refunds(status)`, `sessions(user_id)`, `stock_movements(product_id)`,
`product_reviews(product_id, status)`, `coupon_redemptions(coupon_id, user_id)`. Foreign key
columns are indexed (InnoDB requires it) which keeps joins fast.

## 5. Transactions and locking (where and why)

| Operation | Technique |
|---|---|
| Book a slot | `INSERT IGNORE` the (date, slot) row, then `UPDATE slot_inventory SET booked_count = booked_count + 1 WHERE … AND booked_count < capacity` — 0 affected rows = full → 409 |
| Place order | `BEGIN` → `SELECT … FOR UPDATE` on each product (id order) → guarded `UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?` → insert order/items/ledger → `COMMIT`; any failure → `ROLLBACK` |
| Confirm payment | `SELECT * FROM payments WHERE id = ? FOR UPDATE` → status check (idempotent) → update payment + booking/order in the same transaction |
| Cancel / return | Lock the order row, restore stock with ledger rows, create refund — one transaction |

Isolation level: InnoDB default **REPEATABLE READ**; `FOR UPDATE` takes exclusive row locks so
two customers buying the last unit are serialised — one succeeds, the other gets
"only N left in stock".

`src/db/connection.js › transaction(fn)` gets a connection from the pool, runs
`beginTransaction()`, stores the connection in `AsyncLocalStorage` so every `one/all/run`
inside `fn` uses it, then `commit()` or `rollback()` and finally `release()`.

## 6. MySQL rules worth knowing
* A column used in a `CHECK` cannot also be the column of a foreign key with `ON DELETE
  CASCADE/SET NULL` — that is why `coupon_redemptions` and `payments` use `ON DELETE RESTRICT`.
* `JSON_VALID()` checks keep the JSON columns well-formed.
* Error codes mapped to HTTP responses in `errorHandler.js`: `ER_DUP_ENTRY`,
  `ER_CHECK_CONSTRAINT_VIOLATED`, `ER_ROW_IS_REFERENCED_2`, `ER_NO_REFERENCED_ROW_2` → 409.

## 7. Useful queries for the viva
```sql
-- Revenue by business line
SELECT purpose, SUM(amount_paise)/100 AS rupees FROM payments
 WHERE status IN ('success','refund_pending','refunded') GROUP BY purpose;
-- Low stock
SELECT sku, name, stock FROM products WHERE is_active = 1 AND stock <= 5 ORDER BY stock;
-- Stock ledger must match current stock
SELECT p.sku, p.stock, SUM(m.qty_change) AS ledger FROM products p
  JOIN stock_movements m ON m.product_id = p.id GROUP BY p.id HAVING p.stock <> ledger;
```
